## 측정 방법과 한계

- 측정 작업: 장면 목록 → 프레임별 원본 .bin·label_2·calib 읽기 → F-8 박스 내부 포인트 수(object_features) + F-6 장면별 격자(grid_stats) + F-7 분포 + F-9 기준값·관측 부족 목록 → 결과 저장. 모든 방식이 같은 입력과 같은 출력 파일을 만든다.
- Spark(kitti.bench_job): 장면 목록을 연속 구간 32개로 나눠 mapInArrow 한 번으로 .bin을 읽고, 같은 작업에서 F-8을 numpy 순수 함수로 계산해 작업별 Parquet으로 쓰며 포인트 스트림을 내보낸다. 격자는 그 스트림에 대한 Spark SQL GROUP BY(CAST AS DOUBLE, NaN·ROI 필터 후 FLOOR)다. shuffle 파티션 32, AQE 끔, driver 8g, spark.local.dir = ~/data/kitti/work/bench/spark-tmp (ext4).
- 순차(kitti.sequential): 같은 파일·같은 numpy 함수를 for 루프로 처리, pyspark import 없음.
- 모든 실행은 새 프로세스, OMP/OPENBLAS/MKL_NUM_THREADS=1. 실행 직전 가용 메모리·load average를 기록했다.
- 처리량: scenes/s = 장면 수 / 벽시계 시간, points/s = 입력 .bin 포인트 수 / 벽시계 시간(시작 비용 포함).
- 정확성: 각 실행을 같은 규모의 기준 순차 결과(실행 순서상 첫 정상 종료 seq 반복)와 kitti.verify(F-11)로 대조했다. 기준 실행 자신은 두 번째 seq 반복과 대조했다(두 번째 seq 반복이 없으면 같은 규모의 첫 정상 Spark 실행과 교차 대조하고, 그것도 없으면 대조 실패로 기록한다).
- peak RSS는 100 ms 간격으로 샘플링한 프로세스 트리(실행 Python, JVM, Python worker 등 모든 자손)의 RSS 합의 최댓값이다. 공유 페이지(공유 라이브러리, fork 후 copy-on-write 페이지)는 프로세스마다 중복 계산되므로 실제 물리 사용량보다 클 수 있고, 100 ms보다 짧은 피크는 놓칠 수 있다.
- 페이지 캐시(OS 파일 캐시)는 RSS에 포함되지 않는다. 규모마다 예열 실행 1회로 캐시를 데운 뒤 측정했다.
- 단계 시간은 프로세스 안에서 잰다. Spark의 read_compute는 격자 작업 시작부터 마지막 프레임 작업 종료까지의 벽시계 시간이고, aggregate에는 최종 GROUP BY·grid_stats 쓰기와 F-5/F-6/F-7/F-9 질의가 들어간다. 순차 처리의 aggregate는 0으로 두고 집계 시간은 read_compute(=timings.json read+compute)에 포함된다. other = 벽시계 시간 − 단계 합(인터프리터 시작, import, spark.stop()/JVM 종료).
- 단계 비교 한계: 순차 실행은 집계를 따로 재지 않았으므로(측정 당시 timings.json에 read·compute·write만 있음) phase_breakdown.png와 단계 표의 seq read_compute에는 F-5/F-6/F-7/F-9 집계가 들어 있고 seq aggregate = 0은 '집계 없음'이 아니라 '따로 재지 않음'이다. 따라서 seq와 Spark의 read_compute·aggregate 막대는 단계별로 1:1 비교할 수 없고, 비교는 벽시계 시간(또는 read_compute + aggregate 합)으로 한다. 다시 측정하지 않고는 seq 집계 시간을 분리할 수 없어 값은 그대로 두고 그림·표에 주석만 달았다.
- 속도 향상 범위: 중앙값 비는 seq 중앙값 / 방식 중앙값이고, [최솟값–최댓값]은 seq 최솟값 / 방식 최댓값 .. seq 최댓값 / 방식 최솟값(반복 간 가장 불리한 짝과 가장 유리한 짝)이다.
